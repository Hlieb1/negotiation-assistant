## Етап 0. Вибір моделей під обладнання

### Мовна модель (модуль рішень, варіант Б)

- Обрано **qwen3:8b** (квантування Q4_K_M, 5,2 ГБ на диску). Модель повністю розміщується у відеопам'яті: 5,6 ГБ, 100 % GPU, контекст 4096 токенів.
- Запасний варіант — gemma3:4b, якщо затримка перевищить 5 с. MamayLM (україномовна) — кандидат для порівняння якості української.
- Виміри на запиті з відповіддю одним реченням українською, формат JSON, режим міркувань вимкнено (`think=false`):

| Показник | Значення |
|---|---|
| Перший запит (холодний старт, завантаження моделі в пам'ять) | 115,5 с |
| Повторний запит («теплий») | 4,8 с |
| Швидкість генерації | 16,9 токен/с |

- Висновок: для вимоги «до 5 с для варіанту Б» модель треба завантажувати під час старту сервера (прогрів) і обмежувати довжину відповіді.
- Якість: відповідь граматично коректна українською, формат JSON дотримано.

### Розпізнавання мовлення

- faster-whisper, модель `small`, працює на GPU (float16). Моделі medium + LLM разом займали б близько 7 ГБ із 8, тому почато з small.

### Розпізнавання емоцій за обличчям

- TensorFlow на Windows не підтримує GPU, тому DeepFace працює на CPU. Для 3–5 кадрів/с цього достатньо (див. етап 2).

## Етап 1. Протокол і каркас сервера

- Транспорт — WebSocket, повідомлення JSON (опис у `docs/protocol.md`).
- Затримку `latency_ms` рахує сервер від моменту отримання даних до надсилання підказки, тому розбіжність годинників телефона й ноутбука на неї не впливає.
- Перевірка з тестовим клієнтом (вебкамера + мікрофон ноутбука, 12 с): отримано 44 кадри (~3,7 кадр/с) і 10 с аудіо; затримка підказки-заглушки 80–200 мс.

## Етап 2. Розпізнавання емоцій за обличчям

### Швидкодія детекторів облич (CPU, кадр 640×480)

|---|---|---|

### Порівняння класифікаторів емоцій

Методика: запис із вебкамери ноутбука за сценарієм. Учасник по черзі демонструє 6 виразів по 6 с: нейтральний, радість, злість, здивування, смуток, нейтральний. Аналізується 4 кадри/с. Перші 1,5 с кожного відрізка (зміна виразу) не враховуються. Детектор облич в обох випадках той самий (opencv), обличчя вирізається з полем 10 % ширини. Оцінено 108 кадрів. Скрипт: `server/evaluation/eval_face_recording.py`.

| Класифікатор | Навчальний набір | Точність | злість | радість | нейтр. | смуток | здивув. | Час на кадр* |
|---|---|---|---|---|---|---|---|---|
| DeepFace Emotion | FER-2013 | **29,6 %** | 0 % | 100 % | 0 % | 77,8 % | 0 % | 35 мс |
| HSEmotion enet_b2_7 | AffectNet | **77,8 %** | 100 % | 100 % | 33,3 % | 100 % | 100 % | 40 мс |

\* разом із пошуком обличчя.

Типові помилки DeepFace: нейтральне обличчя і злість визначаються як смуток (у середньому 0,96–0,98), здивування — як страх (0,91).

Інші моделі HSEmotion на тому самому записі (без пошуку обличчя, лише класифікація):

| Модель | Точність | Час на обличчя |
|---|---|---|
| enet_b0_8_best_afew | 69 % | 10 мс |
| enet_b0_8_best_vgaf | 67 % | 10 мс |
| enet_b2_7 | 79 % | 17 мс |

Спроби покращити DeepFace попередньою обробкою (не допомогли, нейтральне і злість так само → смуток):

| Варіант | Точність |
|---|---|
| opencv, вирівнювання обличчя | 29 % |
| opencv, без вирівнювання | 32 % |
| opencv, поле 20 % | 31 % |
| opencv + CLAHE | 31 % |
| yunet | 31 % |
| yunet, поле 20 % | 34 % |
| yunet, без вирівнювання, поле 10 %, CLAHE | 49 % |

Калібрування під людину (ділення ймовірностей на «базовий» вектор нейтрального обличчя, записаного на початку сесії) погіршило точність HSEmotion: 94 % без калібрування на відрізках 2–6, 89–60 % з калібруванням залежно від його сили. Від калібрування відмовилися.

**Рішення:** основний класифікатор — HSEmotion enet_b2_7. DeepFace лишається як варіант у `config.yaml` (`video.classifier`) для порівняння.

Обмеження експерименту: один учасник, одна сесія, бічне освітлення з вікна (одна половина обличчя затемнена), вирази стримані. Для диплома потрібна перевірка на більшій вибірці (етап 7).

### Згладжування

- Ковзне вікно 1,5 с, середнє ймовірностей по кадрах, де знайдено обличчя.
- Якщо обличчя є менш ніж на 30 % кадрів вікна — стан «обличчя не знайдено».
- Обмежувач частоти аналізу з допуском 20 % на нерівні проміжки між кадрами: до виправлення при 4 кадр/с від клієнта аналізувалося 51 з 77 кадрів, після — 57 з 59.

## Етап 3. Аналіз голосу

### Вибір класифікатора емоцій за голосом

- Пошук українського корпусу мовлення з розміченими емоціями (листопад 2026) не дав результату. Існують лише:
  - DRSSU — корпус реального та синтезованого українського мовлення, емоції лише в синтезованій (TTS) частині;
  - EmoBench-UA — емоції в українських текстах, не в аудіо;
  - корпуси для ASR/TTS (Common Voice та ін.) без розмітки емоцій.
- Навчання на англомовних акторських корпусах (RAVDESS, CREMA-D) відхилено: вимога — модель має працювати з українським мовленням.
- **Рішення:** готова багатомовна модель **emotion2vec+ large** (FunASR, Hugging Face `emotion2vec/emotion2vec_plus_large`). Модель попередньо навчена на великому обсязі мовлення різними мовами (самоконтрольоване навчання і дані з автоматичною розміткою емоцій); власного донавчання немає. Модель розрізняє 9 класів; 7 з них відображено на базові емоції системи, класи «other» та «unknown» відкинуто, а їхня сумарна частка зберігається як показник невизначеності.
- Перевірка точності — на власних українських записах за сценарієм (`tools/voice_demo.py --scenario`, оцінка — `evaluation/eval_voice_recording.py`), з порівнянням large і base.
- Ознаки голосу Librosa (тон F0, гучність, темп, паузи, MFCC) обчислюються окремо: вони потрібні модулю рішень і для опису тону співрозмовника, а не для класифікатора.

### Ознаки голосу

| Ознака | Як обчислюється |
|---|---|
| Частка мови, паузи | webrtcvad (кадри 30 мс, агресивність 2) + енергетичний поріг −45 дБ, утримання 3 кадри |
| Частка пауз | частка тиші між першим і останнім мовним кадром |
| Паузи за хвилину | паузи ≥ 0,2 с усередині мовлення |
| Тон F0 | `librosa.pyin`, 65–400 Гц: середнє (Гц), розкид і діапазон 5–95 % (півтони) |
| Гучність | RMS у дБ: середнє і розкид |
| Темп | кількість акустичних онсетів за секунду мовлення (наближення складового темпу) |
| Тембр | спектральний центроїд, 13 MFCC (середні) |

Шумоочищення — спектральне віднімання стаціонарного шуму (noisereduce) перед VAD.

### Перевірка на українському мовленні (перший запис)

Методика: один диктор (автор), мікрофон ноутбука, кімната. Дві ділові фрази («Давайте ще раз обговоримо умови договору.», «Ви пропонуєте саме таку ціну?»), кожна вимовлена з 6 емоціями за підказками на екрані; 12 записів по 5 с. Скрипти: `tools/voice_demo.py --scenario`, `evaluation/eval_voice_recording.py`.

| Модель | Шумоочищення | Точність | Час на запис |
|---|---|---|---|
| emotion2vec+ large | так | **50 %** (6/12) | 33 мс |
| emotion2vec+ large | ні | 42 % (5/12) | 97 мс* |
| emotion2vec+ base | так | 17 % (2/12) | 89 мс* |
| emotion2vec+ base | ні | 50 % (6/12) | 26 мс |

\* перший прогін після завантаження моделі, час не показовий.

По емоціях (large, з шумоочищенням): радість 2/2, смуток 2/2, тривога 2/2; нейтральне 0/2 (→ відраза, смуток), злість 0/2 (→ відраза, смуток), здивування 0/2 (→ відраза, страх). Нейтральної емоції модель не видала жодного разу.

Спостереження:
- Вибірка мала (12 записів, 1 диктор), різниця між варіантами в межах 1–2 записів; висновки попередні.
- Рівень сигналу низький: середня гучність мови від −43 до −31 дБ (мікрофон ноутбука на відстані).
- Зіграна «злість» акустично майже не відрізнялася від нейтральної: гучність −39,7 і −36,7 дБ проти −40,3 дБ у нейтральній, F0 113–129 Гц проти 111–148 Гц. Отже, частина помилок — через стриманість виконання, а не лише через модель.
- Як і для обличчя, модель зміщує спокійне мовлення в бік негативних емоцій (смуток, відраза). Це треба врахувати при об'єднанні (етап 4): вага голосу нижча за вагу обличчя, а «смуток/відраза» з малою впевненістю не вважати сильним сигналом.
- Whisper small на тихому сигналі часто спотворює слова («обовримо мову другу» замість «обговоримо умови договору»); на етапі 7 варто порівняти з medium.

Початкове рішення: emotion2vec+ large з шумоочищенням. Переглянуто після другого запису (нижче).

### Другий запис і виправлення попередньої обробки

Другий запис: той самий диктор, ближче до мікрофона, емоції виражені яскравіше; 3 кола × 6 емоцій = 18 фраз. Із поточною обробкою вгадано лише 4 з 18 (22 %), причому 9 разів модель видала «відразу» з упевненістю 0,94–1,0, зокрема для радості та злості. Гучні фрази доходили до перевантаження (пік −0,3…−1,8 dBFS).

Діагностика на обох записах разом (30 фраз, emotion2vec+ large):

| Що подається в модель | Точність | Хибних «відраз» |
|---|---|---|
| Шумоочищення + VAD, мова без запасу (було) | 33 % (10/30) | 11 |
| VAD без шумоочищення, без запасу | 33 % (10/30) | 10 |
| Весь 5-секундний запис | 57 % (17/30) | 4 |
| Весь запис, нормалізований до −3 dBFS | 57 % (17/30) | 4 |
| VAD без шумоочищення, запас 0,25 с | **57 % (17/30)** | 4 |
| VAD без шумоочищення, запас 0,5 с | 53 % (16/30) | 2 |
| VAD без шумоочищення, запас 1,0 с | 57 % (17/30) | 4 |
| Шумоочищення + VAD, запас 0,25 с | 47 % (14/30) | 8 |
| Шумоочищення + VAD, запас 0,5 с | 47 % (14/30) | 7 |
| Шумоочищення + VAD, запас 1,0 с | 53 % (16/30) | 5 |

Висновки:
- Головна причина помилок — обрізання мови впритул до меж, знайдених VAD: модель втрачає початок фрази та природне затухання голосу. Запас 0,25 с повертає точність до рівня цілого запису.
- Шумоочищення (noisereduce) у тихому приміщенні шкодить: спотворює спектр, і модель частіше бачить «відразу». Крім того, воно займає ~420 мс на фрагмент.
- Нормалізація гучності не впливає на результат.

**Рішення:** `audio.denoise: false`, `audio.speech_padding_s: 0.25` (`config.yaml`).

Результат після виправлення (30 фраз, 5 на емоцію):

| Модель | Точність | злість | радість | нейтр. | смуток | тривога | здивув. |
|---|---|---|---|---|---|---|---|
| emotion2vec+ large | **57 %** | 0/5 | 5/5 | 2/5 | 1/5 | 5/5 | 4/5 |
| emotion2vec+ base | 53 % | 3/5 | 5/5 | 2/5 | 2/5 | 4/5 | 0/5 |

- Large стабільно розпізнає радість, тривогу і здивування, але жодного разу не розпізнала злість (→ тривога, смуток, відраза, здивування).
- Base краще розпізнає злість (3/5), але плутає здивування з радістю (4/5).
- Моделі помиляються по-різному, тож їх поєднання — можливе покращення; перевірити на більшій вибірці (етап 7).
- Обмеження: 1 диктор, 30 фраз; потрібні записи інших людей.

### Перевірка набору DRSSU

DRSSU (Lipianina-Honcharenko et al., Scientific Data, 2025, doi:10.1038/s41597-025-05084-8; дані — figshare doi:10.6084/m9.figshare.25451923, GitHub bohutahennadii/audio_database, CC BY 4.0) — понад 30 тис. реальних і 10 тис. синтезованих записів українською. Призначення набору — відрізняти синтезоване мовлення від справжнього. Метадані містять лише ідентифікатор, тривалість, бітрейт і мітку «реальне/синтезоване». **Міток емоцій немає**: файли синтезованої частини пронумеровані (`generated/0.wav`, …), а згадка про «спектр емоційних станів» стосується лише різноманітності синтезу. На figshare файли позначено як «not publicly available», репозиторій GitHub займає близько 12 ГБ. Для розпізнавання емоцій набір непридатний.

Підсумок пошуку (листопад 2026): відкритого українського корпусу мовлення з розміченими емоціями немає. Найближчий за мовною групою — польський nEMO (amu-cai/nEMO, 9 акторів, 6 емоцій, CC BY-NC-SA 4.0). Інший шлях — власний невеликий український набір.

### Спроби підвищити точність голосового каналу

Ті самі 30 фраз, мова з запасом 0,25 с, без шумоочищення.

| Спосіб | Точність (7 емоцій) | Висновок |
|---|---|---|
| emotion2vec+ large (базовий) | 57 % | — |
| Середнє ймовірностей large і base, вага large 0,5–0,6 | 60 % | +1 фраза; не варте подвоєння моделей |
| SenseVoiceSmall (FunAudioLLM) | 3 % | української не підтримує: мову визначає як китайську/японську, емоцію майже завжди «невідома» |
| Логістична регресія на ембедингах emotion2vec+ large, навчання на одному сеансі, перевірка на іншому | 58 % / 67 % | майже не краще за готову модель; для донавчання потрібно значно більше записів і дикторів |
| Та сама регресія, leave-one-out | 57 % | — |

**Точність на укрупнених класах** (сума ймовірностей емоцій групи):

| Групування | large | base |
|---|---|---|
| 7 емоцій | 57 % | 53 % |
| 5 переговорних станів: злість {злість, відраза}, напруга {страх, здивування}, сумнів {смуток}, згода {радість}, нейтральний | 63 % | 57 % |
| 4 квадранти: негатив зі збудженням {злість, відраза, страх}, негатив спокійний {смуток}, позитив {радість, здивування}, нейтральний | 67 % | 70 % |
| 3 класи валентності: негатив {злість, відраза, страх, смуток}, нейтрально {нейтральний, здивування}, позитив {радість} | **87 %** | 63 % |
| 2 рівні збудження: високе {злість, страх, радість, здивування, відраза}, низьке {смуток, нейтральний} | 77 % | 80 % |

Висновки для проєктування:
- Голосова модель надійно визначає **знак емоції** (негатив / нейтрально / позитив — 87 %), а не конкретну емоцію. Тому на етапі 4 голос використовується переважно як джерело валентності та збудження, а конкретну емоцію дає переважно обличчя (78 %).
- Підвищення точності за рахунок кількох модальностей (обличчя + голос + текст) — основна ідея системи; ефект об'єднання вимірюється на етапі 7.
- Подальше покращення голосового каналу можливе лише з більшим українським набором (кілька дикторів) — тоді має сенс донавчання класифікаційної голови на ембедингах emotion2vec+.
- Реалістичний орієнтир: для розпізнавання емоцій за голосом на чужих дикторах і мові типові 50–70 % на 6–7 класах, і навіть люди погоджуються між собою щодо емоції в голосі лише приблизно у 60–70 % випадків. Точних цифр із джерел тут не наведено, для тексту диплома їх треба знайти в літературі й процитувати.

### Розпізнавання мовлення

- faster-whisper `small`, мова `uk`, GPU float16, beam size 1.
- Фрагменти по 2 с накопичуються у висловлювання; висловлювання завершується паузою ≥ 0,6 с або досягає 10 с і тоді передається на розпізнавання.

### Швидкодія (фрагмент 2 с)

| Крок | Час |
|---|---|
| Шумоочищення (вимкнено, див. нижче) + VAD | ~420 мс (CPU) |
| Ознаки Librosa | ~80 мс (CPU) |
| emotion2vec+ large | ~22 мс (GPU) |
| Обробка фрагмента без мови | 26–31 мс |
| Завантаження і прогрів emotion2vec+ large | 49,6 с (вперше, разом із завантаженням 1,2 ГБ) |

Відеопам'ять: emotion2vec+ large ~0,6 ГБ; разом із whisper small ~1,4 ГБ (без LLM).

## Етап 4. Об'єднання каналів і переговорні стани

Детальний опис методу: `docs/states.md`. Правила: `server/rules/state_rules.yaml`.

### Ключові рішення

- **Пізнє злиття** (зважена сума ймовірностей окремих каналів), а не раннє (об'єднання ознак). Причини: канали мають різну частоту оновлення (обличчя 4/с, голос раз на 2 с); будь-який канал може зникнути (обличчя поза кадром, мовчання); кожен класифікатор можна замінити й оцінити окремо.
- **Різні ваги для різних задач** — висновок з етапів 2–3: для вектора емоцій обличчя 0,65 / голос 0,35 (точність 78 % проти 57 %), для валентності обличчя 0,4 / голос 0,6 (голос визначає знак емоції з точністю 87 %).
- **Просодія відносно норми мовця**: робастні z-оцінки (медіана і MAD) за останніми 30 мовними фрагментами. Абсолютні значення тону й гучності залежать від людини та мікрофона, тож порівнюються лише зі звичною манерою того самого співрозмовника.
- **Вагання** (паузи понад норму мовця) — окремий сигнал для стану «сумнів», бо сумнів у переговорах рідко виражається яскравою мімікою.
- **Синхронізація** за часовими мітками телефона: дані каналу, старші за 6 с від найновішого, не враховуються.
- **Упевненість** = ступінь обраного стану × покриття каналами (1,0 — обидва, 0,65 — лише обличчя, 0,35 — лише голос).

### Перевірка правил на записах етапів 2–3

Очікуваний стан для зіграної емоції: злість → злість; радість → згода; нейтральне → нейтральний; смуток → сумнів; здивування, страх → напруга. Записи обличчя і голосу зроблено окремо, тому кожен канал перевірено окремо; спільну перевірку відкладено до етапу 7.

| Канал | Збіг стану з очікуваним | Основні помилки |
|---|---|---|
| Лише обличчя (108 кадрів, згладжування 1,5 с) | **78 %** | нейтральне → сумнів у 21 з 36 кадрів |
| Лише голос (30 фраз) | **63 %** (для 7 емоцій було 57 %) | злість → напруга (3/5); смуток → злість (3/5) |

По станах для обличчя: злість 18/18, згода 18/18, напруга (здивування) 18/18, сумнів (смуток) 15/18, нейтральний 15/36.

Висновки:
- Укрупнення до станів підвищує точність голосового каналу (57 % → 63 %), бо частина помилок трапляється між емоціями одного стану (страх ↔ здивування).
- Головне слабке місце — зсув моделі обличчя в бік «смутку» для нейтрального виразу: це перетворюється на хибний «сумнів». Можливі виправлення: (1) калібрування апріорних ймовірностей класів на більшій вибірці людей; (2) вища вага сигналу вагання й нижча — смутку в правилі «сумнів». Рішення приймається після збору записів кількох людей (етап 7), щоб не підганяти правила під одного учасника.
- Живий запуск сервера: стан і ступені оновлюються кожні 4 с, затримка підказки 99–170 мс (без модуля рішень).

## Етап 5. Модуль прийняття рішень

Опис методу: `docs/decision.md`.

### Налагодження бази нечітких правил

Перевірка на 10 типових розподілах станів при упевненості 0,15 і 0,5:

| Проблема першої версії | Причина | Виправлення |
|---|---|---|
| Активації всіх стратегій ≈ 0,5, багато нічиїх | базове правило мало належність 1 і «розмивало» центр ваги | належність терму «будь-яка» знижено до 0,2 |
| Сумнів давав нічию «аргументувати» = «уточнити» | два правила для високого сумніву | друге правило переписано на середній сумнів |
| При злості з низькою впевненістю — «уточнити» замість «заспокоїти» | правило «низька впевненість → уточнити» не враховувало емоцію | додано умову «злість і напруга низькі» |
| Напруга + сумнів → «аргументувати» | правило для сумніву не враховувало напругу | додано умову «напруга низька» |

У виведенні Мамдані з агрегацією max слабкий висновок не може «скасувати» сильний, тому заборони виражаються умовами в антецедентах, а не правилами з висновком «слабко».

### Швидкодія і якість: перший замір

Умови: ноутбук **від батареї, режим живлення Windows «Silent»** (GPU працював на 442 МГц із 3090 МГц можливих), 8 ситуацій × 1 повтор.

| Режим | Медіана | p90 | Максимум | Частка запасних відповідей |
|---|---|---|---|---|
| А — нечітка логіка | 17 мс | 36 мс | 75 мс | 0 % |
| Б — LLM (qwen3:8b) | 4374 мс | 4532 мс | 4538 мс | 38 % (таймаут 4,5 с) |
| Гібрид | 4405 мс | 4525 мс | 4531 мс | 50 % |

Розподіл часу одного запиту до LLM: обробка промпту 1199 токенів — 1,14 с при першому запиті і 0,02 с далі (Ollama кешує префікс); генерація 56–66 токенів — 3,6–4,1 с при 15–16 токенах/с. Отже, затримку визначає швидкість генерації, а вона залежить від режиму живлення.

Наскрізна перевірка (вебкамера → сервер → гібрид → підказка): повна затримка 4738 мс, LLM не встигла, тому спрацювала запасна відповідь із варіанту А. Вимогу «до 5 с» дотримано саме завдяки механізму запасної відповіді.

Якість відповідей LLM (якісні спостереження):
- переважно доречні: визнання почуттів при злості й напрузі, уточнювальні запитання при сумніві;
- трапляються русизми («Понятно»), невдалі звороти («дозвольте зняти з вас біль»), неіснуючі слова («застосовуватися як планувалося»);
- модель вигадує факти, хоч промпт це забороняє («у вартість входить доставка, установка та гарантія на 1 рік»). Для реального застосування це ризик, і в гібриді він менший, бо стратегію задано жорстко. Порівняння якості — через анкету експертів (етап 7).

### Технічні проблеми та розв'язання

| Проблема | Причина | Розв'язання |
|---|---|---|
| Не працюють вікна OpenCV, немає `CascadeClassifier` | DeepFace і hsemotion-onnx встановлюють інші збірки OpenCV, які перекривають повну | після встановлення залежностей перевстановлюється `opencv-contrib-python` (`server/setup.ps1`) |
| Сервер падав при завантаженні ваг DeepFace | DeepFace друкує емодзі, консоль Windows (cp1252) не може їх вивести | вивід переведено в UTF-8 у `app/__main__.py` |
| OpenCV 5 не містить файлів каскадів Хаара | зміни в пакеті OpenCV 5 | DeepFace завантажує їх сам у `~/.deepface/weights` |
| Помилка `urllib.request` у hsemotion-onnx | бібліотека не імпортує модуль | модуль імпортується перед створенням моделі |
| Сервер Ollama не стартує з програми в треї | програма не дочікується, поки сервер знайде GPU | сервер запускається командою `ollama serve` |
| PyTorch для RTX 5060 | архітектура Blackwell (sm_120) потребує збірки з CUDA ≥ 12.8 | `torch 2.11.0+cu128` з індексу download.pytorch.org |
| FunASR засмічує лог сотнями рядків під час завантаження | модель пише в кореневий логер | на час завантаження рівень кореневого логера піднімається до WARNING |
| LLM генерує лише 15–16 токенів/с | ноутбук від батареї, режим живлення «Silent» обмежує GPU | для експериментів — живлення від мережі й продуктивний режим; запасна відповідь з А при таймауті |
